## 1. Виды ошибок и чтение traceback

Синтаксическая ошибка не позволяет разобрать программу. Ошибка выполнения возникает во время конкретной операции, например при int("пять"). Логическая ошибка может не вызвать исключения: программа вычисляет неверное среднее, но успешно завершает работу. Для последнего случая нужен известный ожидаемый результат.

Traceback показывает цепочку вызовов и место исключения. Начинайте с последней строки: тип и сообщение. Затем найдите ближайшую строку своего кода. Не пытайтесь исправлять всё сразу. Воспроизведите проблему на коротком входе, определите неверное предположение, внесите изменение и повторите тот же случай.

Печать промежуточных значений полезна в начале обучения, но после исправления отладочный вывод стоит убрать. Иначе тесты и интерфейс будут засорены. При наличии отладчика можно поставить точку останова и посмотреть значения переменных, не меняя программу.

### Демонстрация 1

Полный запускаемый пример: [examples/section_01.py](examples/section_01.py).

```python
try:
    grade = int("пять")
except ValueError as error:
    print(type(error).__name__)
    print("Нужно целое число, например 5")
```

**Ожидаемый вывод:**

```text
ValueError
Нужно целое число, например 5
```

**Вопрос для обсуждения:** Какой тест обнаружит среднее, посчитанное через деление на len(grades)+1?

**Короткое упражнение:** измените один вход примера, до запуска запишите ожидаемый результат, затем объясните расхождение, если оно возникло.

## 2. Проверка данных и raise

Функция должна явно сообщать, что вход не соответствует контракту. ValueError подходит для недопустимого значения. В учебном API мы также договорились использовать его для неподходящего типа входного поля, чтобы новичкам было проще соблюдать один контракт валидации. Это выбранное правило проекта, а не универсальное требование Python.

Оценка допускается только как целое число 2–5. isinstance(True, int) возвращает True, поэтому для этой проверки используем type(value) is int. Преобразование строки "4" в число относится к интерфейсу, а не к модели. Модель принимает уже подготовленное значение и не угадывает намерение вызывающего кода.

Исключение нужно вызвать до изменения данных. Если сначала добавить оценку, а затем проверить диапазон, после ошибки в списке останется неверное значение. Такое повреждение состояния часто проявляется далеко от исходного места ошибки.

### Демонстрация 2

Полный запускаемый пример: [examples/section_02.py](examples/section_02.py).

```python
def validate_grade(value):
    if type(value) is not int or not 2 <= value <= 5:
        raise ValueError("Оценка должна быть целым числом 2–5")
    return value

print(validate_grade(4))
try:
    validate_grade(True)
except ValueError:
    print("Логическое значение отклонено")
```

**Ожидаемый вывод:**

```text
4
Логическое значение отклонено
```

**Вопрос для обсуждения:** Почему int(value) внутри модели может скрыть ошибку?

**Короткое упражнение:** измените один вход примера, до запуска запишите ожидаемый результат, затем объясните расхождение, если оно возникло.

## 3. Обработка ошибок на границе интерфейса

Низкоуровневая функция сообщает об ошибке через исключение. Интерфейс перехватывает ожидаемый тип и показывает понятное сообщение, после чего может повторить действие. Не следует перехватывать все исключения без разбора: так ошибка программирования замаскируется под обычный неверный ввод.

try должен охватывать тот небольшой участок, где ожидается конкретная ошибка. В примере обработка ввода работает со строками и вызывает чистую функцию parse_grade. Число за пределами диапазона тоже приводит к ValueError. Для пользователя достаточно понятного сообщения, а разработчик сохраняет конкретный контракт.

Не используйте except: pass. Он молча скрывает проблему, и пользователь не понимает, сработала ли команда. Если ошибку нельзя исправить на текущем уровне, разрешите ей подняться выше либо добавьте пояснение через raise ... from error. В семестровом меню перехватываются ValueError, KeyError и OSError.

### Демонстрация 3

Полный запускаемый пример: [examples/section_03.py](examples/section_03.py).

```python
def parse_grade(text):
    value = int(text.strip())
    if not 2 <= value <= 5:
        raise ValueError("Оценка вне диапазона")
    return value

for text in [" 4 ", "пять", "6"]:
    try:
        print(parse_grade(text))
    except ValueError:
        print("Введите целое число от 2 до 5")
```

**Ожидаемый вывод:**

```text
4
Введите целое число от 2 до 5
Введите целое число от 2 до 5
```

**Вопрос для обсуждения:** Почему не стоит оборачивать всю программу в except Exception с сообщением «Неверный ввод»?

**Короткое упражнение:** измените один вход примера, до запуска запишите ожидаемый результат, затем объясните расхождение, если оно возникло.

## 4. План тестирования

Тест состоит из подготовки, действия и проверки. Сначала выбираем вход и ожидаемый результат, затем вызываем функцию и сравниваем результат. Ожидание должно следовать из задания и ручного расчёта. Если вычислить его той же формулой с той же ошибкой, тест даст ложное чувство уверенности.

Разбейте входы на категории: обычный случай, пустые данные, границы диапазона, неверные значения и типы. Для оценок отдельные категории — 2 и 5, значения ниже и выше, строка, float и bool. Для списка стоит проверить независимость от исходного контейнера. Один большой сценарий не заменяет небольшие проверки разных правил.

Сравнение чисел с плавающей точкой иногда требует допуска. assertAlmostEqual подходит для среднего, а строки CSV нужно сравнивать точно, потому что формат двух знаков входит в контракт. Выбор проверки зависит от вида результата.

### Демонстрация 4

Полный запускаемый пример: [examples/section_04.py](examples/section_04.py).

```python
def average(grades):
    return sum(grades) / len(grades) if grades else None

assert average([4, 4]) == 4
assert average([2]) == 2
assert average([]) is None
print("Обычный, граничный и пустой случаи проверены")
```

**Ожидаемый вывод:**

```text
Обычный, граничный и пустой случаи проверены
```

**Вопрос для обсуждения:** Почему тест [4, 4] полезен даже при наличии теста [5, 4, 5]?

**Короткое упражнение:** измените один вход примера, до запуска запишите ожидаемый результат, затем объясните расхождение, если оно возникло.

## 5. unittest

unittest входит в стандартную библиотеку. Тесты оформляются методами класса, наследующего unittest.TestCase. Имена методов начинаются с test_. Проверки assertEqual, assertIsNone и assertRaises дают понятные сообщения о несовпадении. Запуск discovery собирает тесты из файлов test_*.py.

В каждом тесте желательно проверять одно правило, хотя для его проверки может понадобиться несколько утверждений. Название test_empty_average сообщает больше, чем test_1. При нескольких сходных входах subTest позволяет показать, на каком значении возникла ошибка, не останавливая остальные подслучаи.

Ниже запускаем набор программно, чтобы демонстрационный пример выдавал предсказуемую короткую строку. В обычном проекте студент будет использовать python -m unittest discover -s tests -v. Успешный запуск требует, чтобы тесты действительно были обнаружены, а не просто чтобы процесс завершился без исключения.

### Демонстрация 5

Полный запускаемый пример: [examples/section_05.py](examples/section_05.py).

```python
import unittest
import io

class GradeTests(unittest.TestCase):
    def test_sum(self):
        self.assertEqual(sum([2, 5]), 7)
    def test_empty(self):
        self.assertEqual(sum([]), 0)

suite = unittest.defaultTestLoader.loadTestsFromTestCase(GradeTests)
result = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
print(result.testsRun, result.wasSuccessful())
```

**Ожидаемый вывод:**

```text
2 True
```

**Вопрос для обсуждения:** Почему сообщение «Ran 0 tests» не подтверждает корректность решения?

**Короткое упражнение:** измените один вход примера, до запуска запишите ожидаемый результат, затем объясните расхождение, если оно возникло.

## 6. Проверка исключения и сохранности данных

Отрицательный тест должен проверять именно ожидаемое исключение. Слишком широкая проверка может принять случайный TypeError за правильно выполненную валидацию ValueError. После исключения полезно проверить состояние: неверная операция не должна оставить частичные изменения.

Например, добавление оценки 6 обязано завершиться ValueError, а прежний список [4] должен остаться [4]. Эти два утверждения проверяют разные стороны одного требования. Если функция просто вызывает raise после append, первая проверка пройдёт, а вторая обнаружит ошибку.

Для загрузки журнала действует похожее правило: создаём новый объект, проверяем все записи и только после успешного возврата заменяем текущий журнал в меню. Так обработка неверного файла не уничтожает уже введённые данные.

### Демонстрация 6

Полный запускаемый пример: [examples/section_06.py](examples/section_06.py).

```python
grades = [4]

def add_grade(value):
    if type(value) is not int or not 2 <= value <= 5:
        raise ValueError("Неверная оценка")
    grades.append(value)

try:
    add_grade(6)
except ValueError:
    pass
print(grades)
```

**Ожидаемый вывод:**

```text
[4]
```

**Вопрос для обсуждения:** Почему pass допустим в этом демонстрационном except, но плох для пользовательского меню?

**Короткое упражнение:** измените один вход примера, до запуска запишите ожидаемый результат, затем объясните расхождение, если оно возникло.

## 7. Тестирование файлов

Файловые тесты должны работать независимо от того, запускались ли они раньше. TemporaryDirectory создаёт временный каталог и удаляет его после блока with. Внутри можно безопасно создавать JSON и CSV, не трогая демонстрационные или пользовательские данные.

Проверяйте содержимое после записи, а не только существование файла. Для CSV полезно читать результат через csv.reader: переводы строк могут различаться по платформам, но строки и поля должны совпадать. Отдельный тест нужен для кавычек и разделителя внутри имени, иначе ручной join может ошибочно выглядеть правильным.

Тест не должен зависеть от сети, случайной даты или порядка запуска других тестов. Если ему нужен файл, он создаёт его сам. Если несколько тестов используют одну подготовку, можно применить setUp, но каждый случай должен получать независимое начальное состояние.

### Демонстрация 7

Полный запускаемый пример: [examples/section_07.py](examples/section_07.py).

```python
from pathlib import Path
import tempfile

with tempfile.TemporaryDirectory() as folder:
    path = Path(folder) / "report.txt"
    path.write_text("Анна: 4.50\n", encoding="utf-8")
    assert path.read_text(encoding="utf-8") == "Анна: 4.50\n"
    print("Файловая проверка выполнена")
```

**Ожидаемый вывод:**

```text
Файловая проверка выполнена
```

**Короткое упражнение:** измените один вход примера, до запуска запишите ожидаемый результат, затем объясните расхождение, если оно возникло.
