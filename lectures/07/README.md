## 1. Структура проекта

Модуль — отдельный Python-файл. Пакет объединяет связанные модули; в нашем проекте это каталог journal с __init__.py. models.py хранит Student и GradeBook, storage.py работает с JSON и CSV, __main__.py содержит консольный интерфейс. Такое разделение позволяет отдельно тестировать модель без запуска меню.

Не следует создавать сложную иерархию каталогов ради самой структуры. Для семестровой работы достаточно нескольких файлов с ясной ответственностью. Главное правило зависимости: storage использует models, а интерфейс использует оба модуля. Модель не импортирует меню и не читает файлы.

Файлы данных и тесты располагаются отдельно от кода пакета. Это помогает увидеть, что является реализацией, что примером входа, а что проверкой. При сдаче включайте исходники и необходимые примеры, но не виртуальное окружение, кэш Python и случайные пользовательские файлы.

## 2. Импорт и точка входа

Импорт выполняет код верхнего уровня модуля. Поэтому бесконечный цикл меню нельзя размещать так, чтобы он запускался при любом импорте. Помещаем работу интерфейса в main, а вызов защищаем условием if __name__ == "__main__". В пакете специальный файл __main__.py выполняется при python -m journal.

Команда должна выполняться из каталога, содержащего папку journal. Если запустить файл journal/storage.py напрямую, относительный импорт from .models может не сработать, потому что модуль потеряет контекст пакета. В README необходимо приводить точную команду запуска, а не только имя файла.

Проверка импортируемости проста: импорт модели не должен ждать ввода и создавать рабочие файлы. Это позволяет использовать публичные тесты, которые импортируют классы и вызывают их непосредственно. Отделение точки входа — практическое условие повторного использования кода.

## 3. Цикл команд

Меню является циклом: показать варианты, прочитать команду, выполнить действие, вернуться к выбору. Для небольшого проекта достаточно if и elif. Номер команды лучше оставить строкой: input уже возвращает строку, а преобразование каждой команды в число создаёт лишнюю возможную ошибку.

Неизвестная команда не должна завершать приложение. Покажите сообщение и повторите меню. Команда выхода должна иметь отдельную ветку. Обработка каждой операции остаётся короткой: получить нужные аргументы, вызвать модель, показать результат. Если внутри ветки появляется сложное вычисление, его стоит перенести в отдельную функцию или модель.

Ниже цикл работает по заранее заданному списку вместо клавиатуры, чтобы пример запускался автоматически. В приложении источник команд заменяется на input, но логика выбора сохраняется. Такой приём помогает сначала проверить последовательность действий без интерактивного ввода.

## 4. Несохранённые изменения

Программа должна различать состояние в памяти и последнюю сохранённую версию. Для небольшого журнала достаточно флага changed. Успешное добавление студента, оценки или удаление устанавливает True. Успешное сохранение или полная загрузка нового журнала устанавливает False. Неудачная операция не должна произвольно сбрасывать флаг.

При обычном выходе с changed=True интерфейс спрашивает, действительно ли пользователь хочет выйти без сохранения. При загрузке другого файла также требуется подтверждение замены несохранённого состояния. Это конкретные требования итоговой работы, связанные с сохранностью введённых данных.

Флаг не заменяет сохранение и не гарантирует восстановление после аварийного завершения процесса. Автосохранение и резервные копии можно добавить как расширение. Для обязательного уровня важно честно показывать, сохранены ли изменения, и не сообщать об успехе до завершения записи файла.

Полный запускаемый пример: [examples/section_04.py](examples/section_04.py).

```python

grades = []
grades.append(5)

# Предположим, функция сохранения завершилась успешно.
changed = False
```

## 5. Безопасная замена при загрузке

Если присвоить book пустой журнал перед чтением файла, ошибка чтения уничтожит прежнее состояние в памяти. Вместо этого load_book создаёт и проверяет новый объект локально. Меню получает готовый loaded и только затем выполняет book = loaded. При исключении присваивание не происходит.

Это простая последовательность «подготовить, проверить, применить». Она полезна и для других операций: импорт таблицы, изменение нескольких полей, массовое добавление записей. Для учебного курса не требуются транзакции базы данных, но сам принцип уже можно использовать.

Проверьте сценарий вручную: ввести студента, попытаться загрузить повреждённый JSON, открыть отчёт. Студент должен оставаться в памяти. Автоматические тесты load_book проверяют отказ на неверном файле, а сохранность текущего журнала в меню требует отдельной проверки интерфейса.

### Демонстрация 5

Полный запускаемый пример: [examples/section_05.py](examples/section_05.py).

```python
book = ["Анна"]

def load_invalid():
    raise ValueError("Повреждённый файл")

try:
    loaded = load_invalid()
    book = loaded
except ValueError:
    print("Загрузка отменена")
print(book)
```

**Ожидаемый вывод:**

```text
Загрузка отменена
['Анна']
```

**Вопрос для обсуждения:** Почему book = [] перед load_book опасно?

**Короткое упражнение:** измените один вход примера, до запуска запишите ожидаемый результат, затем объясните расхождение, если оно возникло.

## 7. Защита проекта

Защита проверяет понимание собственного решения. Студент кратко показывает назначение программы, демонстрирует обычный сценарий и обработку ошибки, запускает тесты и объясняет один участок кода. Важно уметь проследить путь команды: ввод оценки, преобразование строки, поиск студента, проверка диапазона, изменение списка, обновление флага.

Небольшое изменение на защите должно опираться на изученный материал: добавить фильтр, новое поле отчёта или отдельный тест. Оно не должно требовать неизвестной библиотеки. Преподаватель оценивает не скорость печати, а способность найти нужное место, сохранить контракт и проверить результат.

Прохождение публичных тестов подтверждает проверенные требования, но не заменяет ручную приёмку меню и объяснение работы. Дополнительные функции не компенсируют неработающую обязательную часть. Завершение базового сценария и ясный README полезнее незаконченного графического интерфейса.
